# AML Alert Operations Analytics

KPI and KRI reporting, volume forecasting and investigator capacity planning for an anti-money-laundering (AML) alert queue.

> **All data in this repository is synthetic and illustrative.** It is generated by a seeded simulator. No real institution's figures, rates or volumes are used or claimed, and results should be read as a demonstration of the method.

## Operational problem

An AML alert queue has to keep alerts within service-level targets (SLAs) while volume trends upward, shifts seasonally and jumps when a detection rule is launched, and while investigator headcount changes through attrition and new-hire ramp-up. When arrivals exceed what the team can close, the backlog grows, alerts age past SLA and high-risk work is exposed. Operations leaders need leading indicators (KRIs), a view of productivity (KPIs), a volume forecast and an estimate of how many investigators are required.

## Data

`src/simulate.py` generates about 100,000 alerts, 10,000 cases and a roster of about 40 investigators (25 at the start) over 30 months (2024-01 to 2026-06), with a fixed seed. Alert volume combines trend, seasonality, noise and one documented shock (a new detection rule launched June 2025). Each alert carries a creation time, rule type, risk band and score, SLA target, handle time, assigned investigator and disposition; escalated alerts open cases that end in a SAR filing or not. Every assumption and parameter is listed in [`docs/simulation_assumptions.md`](docs/simulation_assumptions.md).

## Approach

1. **SQL KPI/KRI layer** (`sql/`, DuckDB): staging views, calendar and roster dimensions, and marts for monthly KPIs and KRIs, aging snapshots, scenario-level rates, investigator productivity and a RAG scorecard. A small runner (`src/models.py`) executes the files in order. Definitions, grain and thresholds are in [`docs/metric_definitions.md`](docs/metric_definitions.md).
2. **Forecast** (`src/forecast.py`): OLS regression on monthly alert volume with linear trend, one annual sine/cosine pair and a post-launch step. A six-month holdout backtest reports MAPE; a six-month forecast carries 95% prediction intervals.
3. **Capacity model** (`src/capacity.py`): required FTE = forecast volume x handle time / productive hours per FTE (utilization, attendance and business days), compared with ramp-weighted available FTE under three scenarios: base, +20% volume from a further rule launch, and an attrition shock.
4. **Reporting** (`src/figures.py`, `src/report.py`): four figures and a one-to-two-page memo, with every number generated from the model outputs.

## Results

Illustrative results on the simulated data (seed 42; as of June 2026). The memo is [`reports/kpi_kri_memo.md`](reports/kpi_kri_memo.md).

| Metric | Value | Status |
|---|---|---|
| Open backlog (month end) | 2,811 | Red (threshold 2,500) |
| % closed within SLA | 39.5% | Red (target 95%) |
| SLA breach rate | 60.5% | Red |
| Open alerts aged over 30 days | 39.0% | Red |
| Open alerts aged over 60 days | 0.0% | Green |
| High-risk open alerts past SLA | 88.6% | Red |
| False-positive rate / escalation rate | 90.8% / 9.2% | trend only |
| SAR conversion (closed cases) | 34.3% | trend only |

- **Forecast:** holdout backtest MAPE of 5.1% on the last six months; the model estimates the rule launch added about 476 alerts per month.
- **Capacity:** in the base case the staffing gap averages about -0.1 FTE and peaks at +3.0 FTE (November 2026); with +20% volume it averages +4.5 and peaks at +9.0; with the attrition shock it averages +3.0 and peaks at +7.1. Clearing the current backlog over six months adds about 3.1 FTE.

## How to run

```bash
pip install -r requirements.txt
make all     # simulate -> load -> SQL models -> forecast -> capacity -> figures -> report
make test    # pytest: simulator, SQL KPI correctness on a fixture, capacity formula
```

Generated data and intermediate outputs go to `data/` and `outputs/` (git-ignored); the memo and figures are written to `reports/`. Python 3.10+ with DuckDB, pandas, statsmodels, matplotlib and pytest.

## Limitations

- The data is simulated; relationships between volume, handle time, staffing and backlog follow the stated assumptions and are not evidence about any real operation.
- The forecast is fitted on 30 monthly observations with a single seasonal harmonic. Prediction intervals reflect model error only, not future rule changes.
- The capacity model uses average handle time and one utilization figure, and ignores skill mix, holidays and case-stage workload after escalation.
- RAG thresholds are placeholders chosen for illustration, not policy or regulatory limits.
- Before the rule launch, simulated capacity exceeds demand, so the pre-launch backlog is near zero, which is cleaner than most real queues.
